# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a requester-facing TokTickIT ticketing MVP. A temporary Development Requester selector provides the testing context, while the application supports ticket creation, requester-owned ticket discovery, Ticket Detail, and permitted attachment management with a reusable Zen Green responsive UI.

## 2. Stakeholder Request Interpretation

The IT department needs a professional end-user flow for describing a support problem, selecting its category and related system, choosing a requested priority, attaching evidence, and submitting the request. After submission, the selected requester must be able to find only their own tickets, search and refine the list, open a read-only detail view, and manage permitted attachments.

The Development Requester selector simulates a current user only for Lab 2 testing. It is not authentication. Lab 3 will introduce real authentication and must be able to replace this context without changing ticket ownership concepts.

## 3. Scope

### Included

- Development Requester selection and switching.
- Active Category and Related System reference data.
- Ticket creation with backend-generated Ticket Number and initial `NEW` status.
- Requester-owned My Tickets list with search, filters, sorting, and pagination.
- Requester-owned Ticket Detail in read-only view mode.
- Attachment upload, metadata, active download, and soft removal.
- Ownership checks for Tickets and Attachments.
- Loading, validation, success, error, empty, no-results, busy, and responsive states.
- PostgreSQL and Prisma data design, idempotent seed data, REST API, React UI, automated tests, E2E tests, and visual evidence.

### Excluded

- Real authentication, login credentials, passwords, password hashing, sessions, tokens, or role-based authorization.
- IT Staff dashboard, queue, assignment, reassignment, or IT Priority controls.
- Public Comments, Internal Notes, Actions Taken, and collaboration features.
- Ticket status changes after the initial `NEW` status, including resolving, closing, reopening, or cancelling.
- Administration of users, roles, Requesters, or reference data.

## 4. Functional Requirements

- FR-01: The application shall require a selected active Development Requester before ticket screens are available.
- FR-02: The selector shall load active Requesters from PostgreSQL through the API.
- FR-03: The selector shall show loading, empty, failure, keyboard-accessible, and responsive states.
- FR-04: The application shell shall display the selected Requester and provide Change Requester.
- FR-05: The application shall load active Categories and Related Systems from the API.
- FR-06: The Create Ticket screen shall capture Category, Related System, Summary, Requested Priority, Description, and optional Attachments.
- FR-07: The backend shall validate the selected requester, reference data, required strings, allowed priority, and attachment constraints.
- FR-08: A valid ticket shall be stored with the selected requester, backend date, generated unique Ticket Number, and `NEW` status.
- FR-09: The Create Ticket screen shall show field-level validation, submitting, success, and safe failure feedback.
- FR-10: The Ticket list shall return only tickets owned by the selected Requester.
- FR-11: The Ticket list shall support search, filters, deterministic sorting, pagination, and response metadata.
- FR-12: The Ticket list shall distinguish loading, empty-list, no-results, and failure states.
- FR-13: The Ticket Detail screen shall display the owned Ticket as read-only.
- FR-14: The API shall allow an owner to upload a permitted attachment to an owned Ticket.
- FR-15: The API shall return attachment metadata and allow download only for active owned Attachments.
- FR-16: The API shall soft-remove an owned Attachment with a required reason.
- FR-17: Removed Attachments shall remain visible as metadata but shall not be previewable or downloadable.
- FR-18: The frontend shall preserve form values after API failure and prevent duplicate submissions.
- FR-19: All required UI states shall be usable at desktop, tablet, and mobile widths.
- FR-20: The final repository shall include traceable contract documents, tests, review records, AI-use reflection, setup documentation, and screenshot evidence.

## 5. Business Rules

- BR-01: Ticket Number is generated by the backend and is unique.
- BR-02: Ticket Number uses the format `TKT-YYYY-######`, where the final six digits are derived from the persisted Ticket id.
- BR-03: Ticket Date is assigned by the backend and is read-only in the client.
- BR-04: A new Ticket starts with Current Status `NEW`.
- BR-05: The selected Development Requester is a testing context and is not authenticated.
- BR-06: Only active Development Requesters are returned by the selector API.
- BR-07: The selected requester id is stored in browser session storage and sent explicitly with requester-scoped API requests.
- BR-08: Changing Requester clears requester-specific client data and reloads data for the new context.
- BR-09: A Ticket belongs to exactly one Development Requester.
- BR-10: A requester may retrieve, list, upload to, download from, or soft-remove only their own Ticket or Attachment.
- BR-11: An inaccessible or missing Ticket or Attachment returns the same safe not-found behavior so ownership is not disclosed.
- BR-12: Summary is required after trimming and must contain 5 to 120 characters.
- BR-13: Description is required after trimming and must contain 10 to 4000 characters.
- BR-14: Category, Related System, Requester, and Requested Priority are required.
- BR-15: Category and Related System must be active at creation time.
- BR-16: Requested Priority is one of `LOW`, `MEDIUM`, `HIGH`, or `URGENT`; the UI defaults to `MEDIUM`.
- BR-17: The frontend validates before submission and the backend repeats all security-relevant validation.
- BR-18: A submit operation is disabled while it is being processed and cannot create duplicate tickets from one active form submission.
- BR-19: Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF.
- BR-20: Each attachment is limited to 5 MB and each Ticket may have at most five active Attachments.
- BR-21: Attachment validation checks both the allowed MIME type and the allowed extension.
- BR-22: The original filename is display metadata only; physical storage uses a generated safe key and never a user-provided path.
- BR-23: Stored files are kept in API-controlled local storage and are not exposed through an unrestricted static directory.
- BR-24: Attachment metadata includes original name, MIME type, byte size, storage key, upload time, removal time, and removal reason.
- BR-25: Soft removal sets removal metadata and keeps the database record.
- BR-26: A removed Attachment cannot be previewed or downloaded.
- BR-27: Removal requires owner permission, confirmation, and a trimmed reason of 5 to 500 characters.
- BR-28: If an upload fails after Ticket creation, the Ticket remains saved, the failed file is reported, and any orphaned stored file is deleted.
- BR-29: If database metadata creation fails after file storage, the stored file is deleted as compensation.
- BR-30: Re-running the seed does not create duplicate Categories, Related Systems, or Development Requesters.
- BR-31: Search covers Ticket Number, Summary, and Description using case-insensitive matching.
- BR-32: Supported filters are Category, Related System, Requested Priority, and Current Status.
- BR-33: Supported sorts are Ticket Date, Last Updated, and Ticket Number. Default sorting is Last Updated descending with id descending as the tie breaker.
- BR-34: Page numbering starts at 1. The default page size is 10; allowed page sizes are 10, 20, and 50.
- BR-35: Invalid query values are rejected with a safe validation response rather than silently changing the requested query.
- BR-36: API errors use safe user-facing messages and never expose stack traces, database details, or local storage paths.
- BR-37: Lab 3 may replace the explicit requester context with authenticated identity while preserving Ticket ownership relationships.
- BR-38: IT Priority is nullable and read-only in Lab 2. The UI displays `Not assigned` until a later IT Staff workflow sets it.
- BR-39: A trimmed blank search value is treated as no search. A non-blank search is limited to 120 characters.
- BR-40: Requesting a valid page beyond the final page returns an empty `items` array with the requested page and accurate totals; it is not an error.
- BR-41: Initial attachments are uploaded one at a time after the Ticket transaction succeeds. The Ticket and successful uploads remain when a later file fails, and every failed file is reported.
- BR-42: Active image and PDF content may be previewed only through the ownership-checked Attachment content endpoint. Removed content returns the same safe `404` used for missing or foreign resources.

## 6. UI Specification Summary

The UI follows `ui-spec.md` and uses reusable React components for the application shell, labels, fields, field messages, buttons, badges, loading indicators, empty states, error alerts, tables/cards, pagination, and attachment rows.

Required screens and states:

- Requester Selection: initial, loading, active options, no active Requesters, API failure, invalid/no selection, and Continue.
- Application shell: TokTickIT identity, active navigation, selected Requester, Change Requester, and responsive mobile navigation.
- Create Ticket: initial, reference-data loading, validation failure, invalid attachment, submitting, success with Ticket Number, and API failure with values preserved.
- My Tickets: loading, populated list, empty list, no results, API failure, search, filters, sorting, pagination, and Create Ticket action.
- Ticket Detail: read-only Ticket data, attachment metadata, upload, active download, removal confirmation, removed metadata, blocked removed download, and failure.

## 7. Data Changes

The migration preserves all Lab 1 `Category` rows and adds `isActive Boolean @default(true)` plus the reverse Tickets relation. PostgreSQL enum names are `RequestedPriority`, `TicketPriority`, and `TicketStatus`.

| Model | Exact fields and constraints |
| --- | --- |
| `Category` | `id Int @id @default(autoincrement())`; `name String @unique @db.VarChar(100)`; `isActive Boolean @default(true)`; `createdAt DateTime @default(now())`; `tickets Ticket[]` |
| `RelatedSystem` | `id Int @id @default(autoincrement())`; `name String @unique @db.VarChar(100)`; `isActive Boolean @default(true)`; `createdAt DateTime @default(now())`; `updatedAt DateTime @updatedAt`; `tickets Ticket[]` |
| `DevelopmentRequester` | `id Int @id @default(autoincrement())`; `name String @db.VarChar(120)`; `email String @unique @db.VarChar(254)`; `isActive Boolean @default(true)`; `createdAt DateTime @default(now())`; `updatedAt DateTime @updatedAt`; `tickets Ticket[]` |
| `Ticket` | `id Int @id @default(autoincrement())`; `ticketNumber String @unique @db.VarChar(32)`; `ticketDate DateTime @default(now())`; `requesterId Int`; `categoryId Int`; `relatedSystemId Int`; `summary String @db.VarChar(120)`; `description String @db.Text`; `requestedPriority RequestedPriority`; `itPriority TicketPriority?`; `currentStatus TicketStatus @default(NEW)`; `createdAt DateTime @default(now())`; `updatedAt DateTime @updatedAt`; required Requester/Category/RelatedSystem relations; `attachments Attachment[]` |
| `Attachment` | `id Int @id @default(autoincrement())`; `ticketId Int`; `originalName String @db.VarChar(255)`; `storageKey String @unique @db.VarChar(100)`; `mimeType String @db.VarChar(100)`; `sizeBytes Int`; `uploadedAt DateTime @default(now())`; `removedAt DateTime?`; `removalReason String? @db.VarChar(500)` |

`RequestedPriority` and `TicketPriority` contain `LOW`, `MEDIUM`, `HIGH`, and `URGENT`. `TicketStatus` contains only `NEW` in Lab 2. `itPriority` is intentionally nullable so later IT Staff work can set it without changing the requester contract.

Foreign keys are required and use `onDelete: Restrict` for Requester, Category, and Related System. Attachment uses `onDelete: Cascade` because its metadata has no meaning without its Ticket; Lab 2 provides no Ticket deletion endpoint. Required indexes are `Ticket(requesterId, updatedAt, id)`, `Ticket(categoryId)`, `Ticket(relatedSystemId)`, `Ticket(requestedPriority)`, `Ticket(currentStatus)`, and `Attachment(ticketId, removedAt)`.

The backend creates a Ticket with a unique internal placeholder inside one Prisma transaction, derives `TKT-<UTC year>-<id padded to at least six digits>` from the persisted id, updates the same row, and returns only the final value. Attachment bytes use a UUID storage key under `server/storage/attachments/`; the original filename is metadata and is never used as a path.

The repeatable seed upserts the four fixed Categories, seven Related Systems (`Email`, `Campus Wi-Fi`, `VPN`, `LEB2 App`, `Grade Submission App`, `Printer`, and `Corporate Laptop`), and these Requesters by unique email: active `Ariya Anderson <ariya@example.test>`, `Narin Chai <narin@example.test>`, `Pimchanok Dee <pimchanok@example.test>`, and `Kittipong Saelim <kittipong@example.test>`; inactive `Mali Boonmee <mali@example.test>`.

## 8. API Contract Summary

The complete wire contract is in `api-spec.md`. Every requester-scoped request includes `requesterId` explicitly because Lab 2 has no real authentication.

Required endpoints:

- `GET /api/categories`
- `GET /api/related-systems`
- `GET /api/development-requesters`
- `POST /api/tickets`
- `GET /api/tickets`
- `GET /api/tickets/:ticketId`
- `POST /api/tickets/:ticketId/attachments`
- `GET /api/attachments/:attachmentId`
- `GET /api/attachments/:attachmentId/download`
- `DELETE /api/attachments/:attachmentId`

Success responses use 200 for retrieval, 201 for creation/upload, and 200 for a successful soft-removal response. Invalid input uses 400, inaccessible/missing resources use 404, conflicts use 409, oversized files use 413, unsupported file types use 415, and unexpected failures use 500.

## 9. Acceptance Criteria

- AC-01: Given active seeded Requesters, when the selector loads, then only active Requesters are displayed.
- AC-02: Given no selected Requester, when the user tries to enter a ticket screen, then the selector is shown.
- AC-03: Given a selected Requester, when the application shell loads, then the Requester name and Change Requester action are visible.
- AC-04: Given valid reference data, when Create Ticket opens, then Categories and Related Systems come from the API/database.
- AC-05: Given invalid or blank ticket fields, when Submit is pressed, then field-level messages appear and the API is not called.
- AC-06: Given valid ticket data, when Submit completes, then one backend Ticket is saved with matching requesterId, status NEW, and a unique Ticket Number displayed.
- AC-07: Given a valid and an invalid attachment, when the user selects them, then only the valid file is accepted and the invalid reason is visible.
- AC-08: Given a create API failure, when the request fails, then a safe message appears and entered values remain.
- AC-09: Given requester A owns Tickets, when requester A opens My Tickets, then only requester A Tickets are returned.
- AC-10: Given search, filters, sorting, and pagination, when each is changed, then the list and metadata match the API contract.
- AC-11: Given requester B is selected, when requester B requests requester A's Ticket, then the Ticket is rejected with safe not-found behavior.
- AC-12: Given an owned Ticket, when its Detail opens, then Ticket fields are read-only and attachment metadata is visible.
- AC-13: Given an owned Ticket, when a permitted file is uploaded, then active attachment metadata is saved and shown.
- AC-14: Given an active owned Attachment, when download is requested, then the file is returned.
- AC-15: Given an owned Attachment, when a valid removal reason is confirmed, then it is soft-removed and its metadata remains.
- AC-16: Given a removed Attachment, when preview or download is requested, then access is rejected.
- AC-17: Given a mobile, tablet, or desktop viewport, when each screen is used, then controls remain readable with no clipping, overlap, or horizontal page scrolling.
- AC-18: Given the complete requester flow, when the E2E test runs, then creation, ownership, list, detail, and attachment behavior are traceable and passing.
- AC-19: Given a valid list query beyond the final page or with a blank search, when it is executed, then the API returns deterministic metadata without leaking other Requesters' data.
- AC-20: Given an owned active image or PDF Attachment, when preview or download is requested, then the server uses the requested safe disposition; removed or foreign content returns `404`.
